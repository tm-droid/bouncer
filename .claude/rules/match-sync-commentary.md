# match-sync: Commentary Pipeline and Provider Ladder

## The run

`bouncer-match-sync` is scheduled `* * * * *`. It polls the match lists first (`runPoll`), uses the live list in memory and falls back to `live-matches.json` in `cricket-stats`; with nothing live it returns 200 `{skipped:true}` (not an error). Per live match: fetch Cricbuzz live HTML + scorecard → upsert `match-live-detail` → write EVERY new delivery to `match-commentary` → rewrite.

- **Storage is not gated on a viewer.** It once was, and an unwatched match stored one ball per 45 minutes, so the tab showed a sample of the match. `commentaryMatchSet` caps storage at 16 matches per run, viewers first.
- **Every stored delivery is rewritten**, because calls are batched. `commentaryCapFor` gates only the DETAIL tier (scorecard fetch, detail row, scorecard row — a write-budget decision). The slow tier's pass (60 minutes since 2026-09-30, when followed matches started pinging presence) decides detail freshness for a match nobody has open or follows, not prose. Those were 1 and 45 min while groq's 1,000/day was the whole budget; re-derived 2026-09-16 against a ~2,500/day Gemini ladder that was assumed rather than measured (it is ~540), from the measured 11 concurrent unwatched matches. The derivation is above the constants in `main.js` and mirrored **deliberately** in `slow-tier.test.js`: a test that imports the constant it checks cannot catch a wrong constant.
- The watermark seeds from the newest `match-commentary` row (`limit(1)`, one billed read per cold container). It is not persisted to the detail row, because most live matches have none.
- `innings` is stamped **per commentary item** from Cricbuzz's `inningsId`, falling back to the miniscore, then the scorecard length. The old write-time stamp mislabelled an innings' tail as the next innings.
- Env: `APPWRITE_AI_CACHE_DB_ID`, `MATCH_COMMENTARY_COL_ID`, `MATCH_LIVE_DETAIL_COL_ID`, `MATCH_CACHE_BUCKET_ID`, `APPWRITE_API_KEY`, `GROQ_API_KEY` (+ fallbacks), `SENTRY_DSN` (optional; unset disables server-side reporting), `PROBE_SOURCES` (optional).

**Observability (`src/observability.js`).** `@sentry/node`, initialised per container from `SENTRY_DSN`, flushed before every return (the container freezes on return). Reports: raw-text passthrough with per-provider reasons from `generateLine`'s `attempts`; commentary write failures; a viewer-gated match that produced nothing; an unreadable `active-viewers` file (a 404 is normal and quiet); read-budget 402s; **a chain with fewer than two reachable rungs** (error level — generation still works, so every other signal looks healthy while `generateVerifiedLine`'s retry has nobody to fall back to; this went six weeks unnoticed); and **a 429 naming a quota id the per-day latch cannot classify**. The last two are also reported by `generate-commentary`, the only caller talking to providers on a day with no live match. `PROBE_SOURCES=1` turns one execution into an upstream reachability probe (status + bytes + markup markers for Cricinfo and Cricbuzz, from inside the container) and returns without syncing; a manual execution with body `probe-sources` does the same without the variable. Steady-state conditions (chain depth, Cricbuzz unreachable or blocked, the match cap) go through `reportThrottled`; they were one event per run.

**The slow tier is an LLM budget, not a fetch cadence.** `handleRun` does `Promise.allSettled(allLive.map(...))`: every live match has its page fetched and every new delivery stored, every run. `commentaryMatchSet` caps at 16 and `MAX_MATCHES` is 16, so that slice drops nothing; `slowTier` feeds only `commentaryCapFor`, the 10/1/0 **rewrite** budget. `slow-sync-state` looks stale (entries 30+ minutes old) because it is refreshed only for matches that were on the tier; that is not evidence of a 45-minute fetch cadence.

**What loses deliveries is the upstream window.** The live page is a 20-item window, about two overs (`commText=20` across 55 `self.__next_f.push` chunks on three pages). On 2026-09-12 Cricbuzz published nothing for match 161777 for **thirteen minutes** (runs logged `0 new commentary rows`), then republished a backlog jumping `12.5` to `13.4`; 13.1–13.3 never appeared and are absent from the table. `findCommentaryGaps` (`cricbuzz.js`) reports these to Sentry; it deliberately does not count the source over's tail. **There is no backfill**: `/live-cricket-full-commentary/{id}` is client-rendered (zero deliveries server-side), `/cricket-full-commentary/{id}` 404s, `/cricket-commentary/{id}` 307s to the live page. Do not re-investigate recovery without new evidence.

**`MAX_MATCHES` is filled viewers first.** Past the cap a match gets no commentary, no detail row and no win probability. It was 12, sliced in Cricbuzz's list order *before* the viewer set was built; 13 live matches bound it on 2,219 runs in nine days (ANDROID-4P). `liveMatchSlice` puts watched matches first and the cap is 16, bounded by `READ_BUDGET_PER_RUN` (20) because a cold container pays one watermark seed read per stored match. The run log prints the pre-slice count; Sentry hears about a binding cap at most hourly per dropped-id set (`error` if a dropped match had a viewer).

**A finished match is finalised from the recent list.** The final run (last detail and scorecard rows, result alert, summary, `wpe-` log) fires when `syncMatch` sees a terminal status. `belongsOn` (`poll.js`) classifies on Cricbuzz's `state`, so a match moves to `recent-matches` the moment it completes and `syncMatch` never saw it: over 1,100 runs on 2026-10-05/06 not one match was finalised (174057 read "need 87 runs in 56 balls" a day after it was won; 173113 read "Innings Break"). `endedMatches` (`main.js`) takes up to two a run from the recent list — only ids in the poll's `startedIds` — and adds them to that run's set and to nothing published. The `:final` marker is kept by **age** (seven days, a day longer than `startedIds`). Keeping it only while the match was in the newest twenty lost markers on alternate runs: 173691 was finalised 88 times in half a day. A dropped marker is a second finalisation, so count `finalised on` per match in the run logs after touching this. A match finalised more than ten minutes after it was last seen live sends no alert, and the finalising run stamps no probability. **Check a finished match's `match-live-detail` status after any change to which list a match is on.**

**`backlogCtx` is module state and two executions can share a container.** A finishing run nulled the shared variable under the next run (`Cannot set properties of null (setting 'viewers')`, 14:54:38 on 2026-10-03, two executions a second apart on a fresh deployment). Each run holds its own `runCtx` and clears the shared variable only if it is still its own. Anything else at module scope that one run sets and another reads has the same hazard; `contextIo` is re-pointed at the start of every run for that reason.

## Rewriting

**Batched across MATCHES.** Measured 2026-09-16: 6,672 deliveries a day is ~960 calls batched, against ~6,700 unbatched; ~800 high-stakes verify calls came on top, and on 2026-09-24/25 the free ladder ran dry mid-evening UTC (rewrites ~25% until the Pacific reset, then ~94%). The batch is filled by **breadth, not waiting**: `handleRun` runs matches concurrently, ~7 new deliveries arrive per run, and `queueRewrite` coalesces them on a 250ms debounce into one `generateBatch` call. Filling by over would need ~10 minutes against the 0-60s a ball takes now. Cross-match contamination was measured: seven deliveries from seven matches returned 7/7 keys, zero players leaked.

Three rules hold it up:

1. **Lines are matched by `[matchId|ball]` key, never by position.** A dropped or reordered line must leave that delivery absent; a confidently wrong line is far worse than a raw one.
2. **Every queued promise must resolve**, including when the batch throws; one unresolved promise costs the run its 120s timeout. Pinned by the `__setBatchFn` seam, because `generateBatch` returns an empty Map rather than throwing.
3. **Every rewritten line is fact-checked in one batched call** — `verifyBatch`, inside `flushBatch` right after `generateBatch`, each line against its own raw text, verdicts matched by key. Until 2026-09-25 only wickets and boundaries were checked, one call each (per-line for every ball would be ~6,500 calls a day). It fails closed: FAIL is `verification_failed`; an unanswered key or no checker is `verifier_unavailable`.

The checker: six planted errors (four→six, wrong fielder, lbw→bowled, wrong thrower, bowler batting, invented milestone) were all caught 3/3 via qwen (~700ms for 14 lines) and 2/2 via the Gemini fallback. It is sent the ball number with each source ("Ball 58.6: …"); without it "closes the over" was unverifiable. Its rules separate FACT (who, runs, outcome, dismissal, fielder, anything about the over, innings or match — a "maiden", a "fifty partnership") from COLOUR (line, length, a defensive push), tuned 2026-09-25 against its own `[VERIFY-FAIL]` log lines, which carry the rejected text because nothing else stores it. qwen scored 14/14 × 3; the Gemini fallback misses over/innings claims (passed "a maiden over" 3/3), so qwen staying reachable matters. The rules follow `SYSTEM_INSTRUCTION`'s licence ("the atmosphere is yours — the facts are not"): a checker stricter than the writer's brief rejects most good lines. The batch prompt carries the raw Cricbuzz line alone; per-match score context in a cross-match batch becomes a fabricated fact. `verifyBatch` takes `writtenBy` and asks models that did not write the lines first.

**A batch key is thirteen digits and a model miscopies them.** `generateBatch` matched a reply line by the exact `matchId|ball|timestamp` tag. For `169910|26.4|1791530585051` gemini-flash-lite answered `…585050` four times of four; the line was dropped with nothing in `attempts` and read as `providers_exhausted` for two hours (ANDROID-4Z). A tag whose match and ball belong to exactly one delivery in the batch is now that delivery's; two deliveries sharing a label (a wide and the next ball) are told apart by timestamp alone and a miscopy between them is dropped. A dropped tag is written to `attempts`. **`providers_exhausted` with no attempt recorded means an answer was thrown away.**

**Raw Cricbuzz text is never stored.** Measured 2026-09-26/27: 133 of ~5,400 rows were raw, ~90% `verification_failed`, and the checker was right (groq had Lomror batting while he was bowling, a whole batch of six). One rejection with no second attempt was the leak.

- `rewriteWithRetry` (`main.js`) gives every rejected or dropped delivery **one** more writer call in the same run, `exclude`-ing the failed rung; it re-samples the same rung only when no other writer answers. A batch nobody answered is not retried.
- Anything still unverified goes to the **rewrite backlog**: `holdDelivery` stores everything the row needs (the ball will not be on the ~20-item page later), the watermark still advances, and the late row carries its original `sort_key`, which the device's `sortKey`-positioned insert places correctly.
- Since 2026-10-03 a held delivery mostly rides in spare slots of a fresh batch (`flushBatch` → `takeHeld`): Gemini rungs are limited by requests a day, and a typical batch carried 6.95 of 12. Batch size stays `BATCH_MAX_ITEMS` (12), the size the writer and checker were probed at.
- Order is `backlogOrder`: matches someone has open, then other live matches, then finished ones, **newest ball first** in each (it was oldest-first across everything).
- `drainBacklog` sends dedicated batches, two a run (`BACKLOG_DRAIN_PER_RUN`, 24), also on runs with nothing live. A FINISHED match gets them only while its backlog is ≤ 24 or in the 3 hours before the Pacific reset (`dedicatedEntries`).
- **Nothing is ever dropped and there is no age limit** — an explicit decision; do not add an expiry.
- A delivery held during a run is not offered again in that run; `inFlight` keeps one held delivery out of two batches.
- Persisted as `rewrite-backlog` in `cricket-stats`, written only when it changes, never over a file this container failed to read.
- **A held delivery's alert is sent when it is first seen** (a late wicket alert is past `ALERT_MAX_AGE_MS`); the drain sends none. Held balls count as present for `findCommentaryGaps`.
- `reportThrottled("rewrite-backlog")` fires past 15 minutes or 200 held. Pinned by `rewrite-backlog.test.js`.
- A "who bowls, who bats" rule in the writer prompt was probed on groq over 36 real rejected deliveries: it cut role swaps without reaching zero, so it was not shipped. The checker catches them and the retry replaces them.

**A source can contradict itself.** Match 151554's 15.5: header "Gudakesh Motie to Ruturaj Gaikwad, 1 run", description "Rohit Sharma carves it". The checker failed every rewrite for an hour (~240 calls on a ~1,330-call day) and what passed was groq echoing the raw text, stored as `ai_generated: true`. Guards since 2026-10-03:

- `sourceConflictNote` appends a scorer's note to the text both writer and checker read (fires only when the description names the other live batter and not the header's; without the note in the checker's copy the correct line failed 3/3).
- `isEcho` drops a line that is the source again, so it gets its retry.
- A held delivery's `rejections` count stops dedicated batches at `HELD_STUCK_REJECTIONS` (3) — it still rides in spare slots and the pre-reset sweep, and is never dropped — and raises one **error**-level Sentry event naming the ball. Before, the only report was the hourly "Commentary is being held" warning (ANDROID-4Z).

**A delivery is not one row, and the ball label is not its identity** (audited 2026-10-03 over 1,500 rows). Cricbuzz republishes a corrected delivery under a new timestamp and the row id is the timestamp's hash, so the withdrawn version stayed (171061's 10.3: a single, a catch that never happened, the single again). `supersedeOlder` (`main.js`) deletes the older **legal** row for the same innings and label when a newer one is written — in memory per container; the device rule covers a cold start. A wide or no-ball carries the label of the legal ball that follows, and labels repeat next innings; the device side is `deliveryKey` (see `match-detail-and-commentary-ui.md`). Pinned by `commentary-supersede.test.js`.

**A source with no description is written in code.** "Chinelle Henry to Mupachikwa, no run" has nothing to rewrite, and the writer invented a length, a shot and a field position (matches 173107, 174881), which the checker passes as colour. `plainLine` (`main.js`) writes those from bowler, batter and outcome with `provider: "template"`, `ai_generated: false`; a dismissal still goes to the writer. About a quarter of deliveries on an associate-heavy day, none costing a call. `keepsScorerText` rejects a model line that kept the scorer's header or scorecard tail (exact-match `isEcho` let 24 through in those 1,500 rows).

**The checker rules were not why contradictions were stored.** Four stored contradictions (163077 89.1 "left alone" → "defends it back down the pitch") all FAIL under the existing `VERIFY_BATCH_RULES`, 3/3 on qwen and `gemini-flash-lite-2`, in isolation. A reworded rule scored the same, so nothing changed. Why they passed in production is not established.

**An overturned review is not a wicket.** Cricbuzz writes the on-field decision and the review in one item ("…, no run, … given OUT LBW, but he reviews … survives"), so every dismissal pattern fires. `classifyEvent` (`llm.js`) and `TimelineEventExtractor.isWicketLine` both read `outcomeClause` — the field after "<Bowler> to <Batter>," — before any marker in the prose: a clause stating runs means nobody was dismissed. `outcomeClause` lives in `llm.js` (which `cricbuzz.js` imports) because `llm.js` is vendored byte-identically into `generate-commentary`, which has no `cricbuzz.js`.

**Three monitors reported things that were not so (2026-10-09).** `findCommentaryGaps` walks a batch in timestamp order, which does not always follow the over (26.1–26.4 written, 26.3 and 26.4 reported lost, ANDROID-5H); a label elsewhere in the same batch is no longer missing. `disagreement` compared short names by a shared word ("Ahmadzai" vs "Yamin", ANDROID-5C); it now takes `playerNamesOf(detail)`, the full names on the match's own Cricbuzz pages. Remaining `batter`/`runs` disagreements are the sites labelling balls one apart after an extra, and leaving the second report out there is correct. FCM's one retry followed a 429 at once; it waits a second now (ANDROID-50).

## Match-situation lines, preview, summary

**Situation lines are event-driven** (`situation.js`). A row with a blank `ball`, `provider: "situation:<rung>"`, written only on a trigger: the same batter's last 2 balls faced both sixes or last 3 all boundaries; a bowler's 2 wickets in an over (run-outs excluded); 3 wickets in 18 balls; a 0.15 win-probability move inside 15 minutes; a side first crossing 0.90. There is **no fixed interval** — a user decision; do not add one. The writer sees structured facts only and `validSituationLine` checks in code: every number, counted quantity and capitalised word must be in the facts. A failed line is dropped, never retried. Stored when its over ends (`sort_key` = the next over's first ball − 1), because a non-delivery row mid-over splits the over into two blocks on the device. Win-probability triggers are skipped for Tests and outside the detail tier.

**`stateTrigger` adds three context triggers**: a batter crossing 50/100/150/200 (with their record in the archive's matches of that format), a partnership passing the same marks, and a first innings ending at a ground whose `typicalFirstInnings` the context knows. Each remembers what the last run saw, so a cold container that first sees a batter on 73 says nothing. `UNBACKED_RE` is not an outright ban: a line may say "half-century" only when its facts do, and only a milestone trigger's facts do. **"career" is never in the facts** — Cricsheet is the matches it recorded ("5210 runs in 131 recorded one-day innings"). A spelled-out number ("sixty-four balls") fails the line, correctly.

**Preview and summary are never unchecked prose** (`surfaces.js`, stored on `mc-{matchId}`). Facts are built in code — head-to-head, the ground's usual score, toss, forecast, pre-match chance; or the result, each innings, top scorer, best bowling. One writer call; `validSurface` requires every sentence grounded on its own, both sides named, weather called a forecast; then the batch fact-checker runs with the facts as its source (the code check cannot see a number given to the wrong side). Any failure stores the same facts as plain sentences (`provider: "template"`). Probed 2026-10-03: 8 of 8 passed both. A preview needs two things beyond the fixture or it is not written; a summary is written on the finalising run.

## Cricinfo as a second source

`/series/{slug}-{id}/{slug}-{id}/ball-by-ball-commentary` is server-rendered: `__NEXT_DATA__` → `props.appPageProps.data.content.comments` is ~19 deliveries (three overs), and `content.innings[].inningOvers` is **every completed over of every innings**. Measured 2026-10-06 from the Appwrite container: 200, ~900 KB, 250 ms. `?fromInningOver=` is ignored; `/_next/data/…` and `hs-consumer-api` are 403. So the window is polled every run for every joined live match and kept in memory (`cricinfoMatchStep`, `main.js`). A match joins by both team names plus start time within 12 h (`joinCricinfoMatch`); a delivery by innings + ball label (`18.6` ≡ `18.6`). A wide or no-ball is never joined. Prose exists only where `ballByBallSource` is `"feedback"` — internationals and A tours, 2 of 8 live matches when measured.

- **Second report.** When the sites agree on bowler, batter, runs and wicket (`disagreement`), the text gains ` [Second report: …]`, read by writer AND checker (`BATCH_SYSTEM_INSTRUCTION`, `VERIFY_BATCH_RULES`). Cricinfo's text is never stored; `isEcho` drops a line carrying it whole. A bare scorer's line is templated (`plainLine`) only when Cricinfo has no description either. Nothing waits for the second site.
- **Gap fill.** A hole between two of a run's Cricbuzz deliveries is filled from Cricinfo's (`cricinfoFills` → `asCricbuzzLine`), through the same rewrite, check and hold. `provider` ends `+cricinfo`; `sort_key` is the ball before the hole plus 1, 2, 3 ms. A label this container already stored is not a hole.
- **Over history.** `fillOverHistory` adds only overs the history lacks; a Cricbuzz reading and its stamped `p` are never replaced.

**Everything from that page is untrusted, and the cleaner is an allowlist.** `promptSafe` (`cricinfo.js`) keeps Latin letters, digits, spaces and sentence punctuation — **no colon, no bracket, no line break** — because the prompt's structure is `[key]:` tags, `Source:` labels and bracketed notes. Four denylist versions each missed a case (nested entities, a lone surrogate joining two halves of a label, full-width colons, look-alike scripts); do not go back to one. A header and a dismissal are not cleaned: each must BE its shape or is dropped. Bodies are size-capped while read (`readBounded`). An allowlist cannot stop a plain-English instruction; the writer is told both accounts are reported text, and the checker and `carriesLink` gate what is stored. A 403/429 latches every Cricinfo request for an hour and reports at error level; any other failure latches that one match. A request with **no answer** (the 8 s timeout, a dropped connection) is asked again in five minutes and only the third in a row costs the hour (`askAgainSoon`); one timeout used to cost the hour and raise an error (ANDROID-5E, 32 in two days).

**Info tab and wagon wheel.** `matchFacts` puts umpires, TV umpire, referee, debutants and reviews left on `mc-{matchId}` as `cricinfo`, written only when changed. `match-statistics` carries `batsmenPerformance[].wagonData` — eight zones summing to the batter's runs — **for the two batters at the crease only**, so `cricinfoWagonStep` keeps the latest snapshot per batter (detail tier, at most every scorecard interval) and publishes `scorecard.wagon`; the device shows the runs and balls the snapshot covers. Zones are octants clockwise from the top, bowler's end at the bottom, not mirrored for a left-hander (verified against per-ball coordinates). **The pitch map is not shipped**: `bowlersPerformance[].{lhb,rhb}PitchMap` has numeric `line`/`length` codes not yet verified against per-ball `pitchLine`/`pitchLength` names — do that on a live covered match first.

## Provider ladder

**The ladder since 2026-09-25.** Writers: `gemini-flash-lite` → `gemini-3.1-flash-lite-preview` → `groq` (gpt-oss-20b) → `gemini-3.6-flash` → `gemini-3-flash-preview`. Plus `groq-qwen` (`qwen/qwen3.8-27b`), **`verifyOnly`**: asked first for every verdict, never asked to write (`rungsFor(purpose)`). Probe verdicts: the preview model had no factual error in 3×11 hard deliveries; qwen invents names when writing ("Babar Zaman") but was perfect as a checker in 2 tokens.

**Rejected rungs — do not re-add.** `gpt-oss-120b` ("bowled LBW" 3/3); `gemma-4-*` (time out or emit raw `<thought>`); `gemini-omni-*` and `gemini-3.1-pro-preview` (no free quota); `antigravity-*` (Interactions-API only); `gemini-3.1-flash-lite` (dropped "ramp", invented "sharp bouncer" — a hallucination ships, a timeout merely falls through); `gemini-3.7-flash` and `gemini-flash-latest` (16s timeout / 503 against a 15s `AbortSignal`); the Pro ids (429 on the first call); every `gemini-2.5-*` (404, "no longer available to new users" — `gemini-2.5-flash-lite` is listed in `/v1/models` and still 404s); **OpenRouter `:free` models** ("temporarily rate-limited upstream" 429 on every call). Cerebras and sambanova left `PROVIDERS` and stay in `probeProviders()` alone, which is how a funded account would be noticed. Pinned by `provider-ladder.test.js` in both function dirs. All rungs were probed against the real `SYSTEM_INSTRUCTION` on wicket/dot/six fixtures before being added: the model list is not the set of models a key can call.

**Measured limits. Never infer a rung's limit from a sibling model** — read it at https://ai.dev/rate-limit or from its first per-day 429.

- Gemini's free quota is per project PER MODEL (the 429 body carries `quotaDimensions: {model}`). Both flash-lite models: 15 RPM / 250K TPM / 500 RPD (`gemini-3.5-flash-lite`: 15 RPM from a 429 `quotaValue` on 2026-09-16; the per-day and token figures are read from AI Studio, the only place Google publishes them). `gemini-3.6-flash` and `gemini-3-flash-preview`: **20 RPD** (`GenerateRequestsPerDayPerProjectPerModel-FreeTier`, `quotaValue: "20"`, production 2026-09-24). The 2026-09-16 sizing of "≈ 2,500 calls/day" assumed 500 for all three ids; real Gemini supply is **~540/day**.
- `gpt-oss-20b` and qwen: 30 RPM / 1K RPD / 8K TPM / **200K TPD**; the token cap binds on both (groq hit it ~04:30 UTC on 2026-09-25).
- One project supplies ~1,330 calls a day (qwen ~160 checks, flash-lite 500 + 500, gpt-oss ~130, the two reasoning rungs 40), against ~2,400 for the measured busy day (6,672 deliveries) and ~2,930 for 16 matches bowling for 8 hours.
- **The checker is the ceiling**: qwen is token-bound at ~117 tokens a delivery, so ~1,500 deliveries a day; every check past that lands on a Gemini writer rung — the weaker checker, and double the burn on that rung.

**More Gemini projects.** A second PROJECT is four more buckets; a second key on the same project is none. `PROVIDERS` lists each Gemini rung once; `ladder()` adds a `-<n>` twin behind it for `GEMINI_API_KEY_2` (`account: "gemini-2"`; always listed, skipped as `no GEMINI_API_KEY_2` when unset — rung names are stored in `match-commentary.provider` and key the per-day latch, so they must not move) and for `GEMINI_API_KEY_3`…`_20` when set. Same model ids, prompts and floors, so probe verdicts carry over. `dailyExhausted` is keyed by rung name and `paymentBlocked` by account, so projects latch independently (pinned in `provider-ladder.test.js`). One line asks at most twelve rungs over the network and walks at most 45 s: with ten projects there are forty Gemini rungs, and an unbounded walk was one request reaching every project's quota.

**Traps that look like free capacity.**

- **An alias is not a bucket.** Bursting `gemini-flash-lite-latest` returns `quotaDimensions: {"model":"gemini-3.5-flash-lite"}`.
- **A reasoning rung needs its own `tokenFloor`.** `gemini-3.6-flash` at `max_tokens: 512` returns `completion_tokens: 18` against `total_tokens: 717`, `finish_reason: length`; those two rungs carry `tokenFloor: 2048`, flash-lite keeps the caller's 100.
- **A per-day 429 is not a per-minute one.** `unavailable` is per-line because a rate limit clears by the next ball — true of the 15 RPM bucket, false of the per-day one, so `dailyExhausted` latches until the Pacific reset. Both quotaIds are observed verbatim; `drainUnknownQuotaIds` reports any 429 matching neither.
- groq's per-day 429 is prose ("tokens per day (TPD)"), not a QuotaFailure, so it latches 30 minutes (`GROQ_DAY_LATCH_MS`); without it an exhausted groq rung was re-asked 399 times in one night.

**A hang is not a refusal.** An endpoint that times out is skipped for the rest of the walk and the line (every Gemini rung is one endpoint, so a Google hang used to spend the whole 45 s and never ask groq); a 429 still falls through to the next rung on the same endpoint. `deadlineAt` spans every walk of a request, and match-sync stops asking providers 90 s into a run.

**The verify call's token budget is sized by thinking, not by the answer.** Every provider is a reasoning model (groq runs `openai/gpt-oss-20b` with `reasoning_effort: low`) and reasoning tokens come out of `max_tokens`. At `maxTokens: 16` groq returned an *empty completion* on verify while answering generate (100) perfectly, and with cerebras and sambanova on 402 the fact-check failed closed on every delivery: that is all of ANDROID-38 (1,858 balls stored raw). 64 was measured insufficient in production; it is 256, pinned by `verification-scope.test.js`. 256 was still not enough for groq (`groq: empty completion (length)` on every verify on 2026-09-25, so each high-stakes ball fell to the two 2048-floor Gemini rungs, ~800/day, spending both 20/day buckets — ANDROID-4T, and ANDROID-38 again). groq carries `tokenFloor: 1024` in `PROVIDERS`; the floor lives on the rung, not in `verifyLine`. An `empty completion` note carries its `finish_reason`: `length` (spent budget) and `stop` (answered nothing) need opposite fixes. A line generated but verifiable by nobody is `verifier_unavailable`, not `verification_failed` — a spent chain versus a hallucination.

**A 402 is account state.** Measured 2026-09-15: `GET /v1/models` returns **200** on all three providers and lists both model ids, while `POST /chat/completions` returns **402** on every model — Cerebras `{"type":"payment_required_error","param":"quota"}`, SambaNova `{"balance_units":0,"code":"PAYMENT_METHOD_REQUIRED"}`. A model a key cannot reach answers **404 `model_not_found`** (what `c324d5b`, `82b467b` and `3bcf060` fixed); no model swap escapes a 402.

- `unavailable` is per-line, so a 402 provider was re-asked on **every delivery** (two doomed round trips at 15s each) for six weeks. `paymentBlocked` (`llm.js`) is module-scoped and holds for the container's life; the skip is still written to `attempts`.
- `deadProviders` counted **429 only**, so a 100%-402 provider never reached `rateLimited === calls`. The tally now counts any non-200 with the dominant status, and a 402 **skips `DEAD_PROVIDER_MIN_CALLS` entirely**: one 402 is conclusive, and once latched the provider can never be called enough to clear a ratio. Pinned by the 402 cases in `verification-scope.test.js`.

**The chain needs a second reachable provider.** `generateVerifiedLine` retries a failed verification with `exclude: [used.provider]`; on a groq-only chain that retry has nothing to call, returns null, and every FAIL becomes `verification_failed`. Paying for groq does not change that. Groq's free tier is also 1,000 requests **per day** (`x-ratelimit-limit-requests`) and 8,000 tokens per minute.

**Coverage history, for sizing.** Measured 2026-09-16 over 13 days: **94 `ai_generated = true` rows/day** average, 367 on the busiest day; ~11% of groq's 1,000/day on its own; **0.7-8.3% of stored commentary was AI-written** (the tab was 91-99% raw text). That was not an RPD problem: it was `commentaryCapFor` returning 0 for unviewed matches, the slow tier's interval × per-pass cap, and verification failing closed on a one-rung chain. `SLOW_TIER_INTERVAL_MS` was 45 min only because 1,000/day was the whole budget (`main.js` records the 15-minute option being rejected at 768/day). Concurrency over 312 hours: **mean 2.87 matches bowling at once, 4.28 while any cricket is on, p90 10, peak 13**, 33% of hours none. Count a match live only if it wrote a commentary row that hour — an open `match-live-detail` window says 7.06/19, because a Test holds its row open overnight.
