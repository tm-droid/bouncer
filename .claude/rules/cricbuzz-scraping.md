# Cricbuzz Scraping

**Gender is read off the names** (`network/MatchGender.kt`). Cricbuzz's list has no gender field and the scraper wrote a constant `"Men"`. Home's two filters are `HomeFilters` (`ui/HomeFilters.kt`), saved on change and restored once per ViewModel; All matches reads `statusMatches`, the selected status before those filters.

**An empty Upcoming list is Cricbuzz's state, not a broken page.** `live-scores/upcoming-matches` sometimes shows "Nothing to show" while fixtures exist; the ~90 matches the scraper still parses there are the site-wide live ticker, which the PRE_MATCH filter correctly rejects. Do not switch the source: `/cricket-schedule/upcoming-series/…` lists series schedules, and switching to it was reverted. When the scrape is empty, `LiveActivityViewModel.updateMatches` serves `MatchCacheService.lastKnownUpcoming()` — the last non-empty Upcoming list this device saw, minus fixtures whose `startDateMs` has passed. The `upcoming-matches` Storage file cannot stand in (overwritten with the same empty list, no start times). Pinned by `UpcomingFallbackTest`.

**Series pages need the slug.** `/cricket-series/{id}/{tab}` answers 200 with no data; only `/cricket-series/{id}/{slug}/{tab}` carries it, so `seriesSlugOf` reads the slug off the unslugged page (`SeriesDetailScraper`, `PointsTableScraper`).

- Schedule walks `matchDetailsMap` groups — never bare `matchInfo`, which is also the site-wide ticker. It opens on the next match (`scheduleAnchorIndex`, pinned by `SeriesScheduleAnchorTest`).
- Stats is `/stats?statsType=X`, server-rendered per type; one page carries every format's table (`initialStats.{odi|t20|test}StatsList`). A series that has not started has no stats section — the normal answer, not drift.
- The Series tab's Past view is `/cricket-scorecard-archives/{year}` (sections `internationalData`/`leagueData`/`domesticData`/`womenData`); `/cricket-schedule/series/all` is current and upcoming only.
- Pinned by `SeriesDetailFlightTest` and `SeriesListMergeTest`.

**Team sheets come from `/cricket-match-squads/{id}`, fetched by `MatchDetailViewModel` when a match opens, and asked again every 10 minutes until both elevens are named.** Whether the match screen offers a Squads tab depends on it. It is server-rendered (unlike `/live-cricket-over-by-over/{id}`, client-rendered with no per-over data — the same dead end as the full-commentary page). Its flight stream holds `{team1: {team, players}, team2: …}` where `players` is keyed `"playing XI"` + `"bench"` after the toss and `"Squad"` before. `MatchSquadsRsc` parses it; `MatchSquadsSource` caches an XI for the process and a pre-toss squad for 10 minutes. No Appwrite cost. Aligned to `match.teams` by team id. Pinned by `MatchSquadsRscTest` against both captured shapes.

**Profile pages are App Router.** `/profiles/{id}/{slug}` has no `__NEXT_DATA__` block — only `self.__next_f.push(...)` chunks — and the legacy Jsoup selectors (`cb-font-40`, `cb-plyr-inf`, `cb-plyr-thead`, …) match **zero** elements, so both of `PlayerProfileScraper`'s original strategies produced a profile with a name and nothing else rather than an error. `PlayerProfileRsc` reads the flight stream via `forEachNextFlightPayload` (the parser the match pages use) and runs first; the other two stay as fallbacks. Pinned by `PlayerProfileRscTest` against captured markup.

**Scorecard player names are in a span, not the row's link.** In a `div.grid.scorecard-bat-grid` / `scorecard-bowl-grid` row the only `<a>` elements are a hidden per-player menu ("View match performance", then "View profile" → `/profiles/{id}/{slug}`); the name is in a `span` whose class carries `hover:underline`. `row.select("a").first()` named **every** batter and bowler "View match performance"; those went to `match-scorecard` and the Scorecard tab's `items(..., key = { it.name })` threw `IllegalArgumentException: Key … was already used` (Sentry ANDROID-40). `playerNameOf` (both `CricBuzzParser.kt` and `match-sync/src/cricbuzz.js`) reads the span first and falls back to a non-menu link. Pinned by `CricBuzzScorecardRowFilterTest` against captured markup, with `cricbuzz.js` declared as a Gradle test input. **Never key a lazy list on scraped text** — keys must include the index.

**The same menu is in the fall-of-wickets cell, and partnerships are a different grid.** A `div.grid.scorecard-fow-grid` row has three cells; the first holds the name span *and* the hidden menu, so both parsers named every dismissed batter `KL RahulView match performanceView profile`, and `mapFallOfWickets` (which looks the batter up in `innings.batsmen` by name) then showed `0 (0)`.

- `score` is the **runs half alone** (`"37"`, not `"37-1"`) in both parsers. The match phases read it with `toIntOrNull`, for which the joined form is silently 0; `currentPartnership` reads only the leading run count, and the innings `score` and `overs` it pairs with arrive as `"156-4 f/o"` and `"54 Ov"`.
- Partnerships render as `div.scorecard-pship-grid`, never as fow-grid rows; the header walk looking for a "Partnerships" section among them returned nothing, so `innings.partnerships` was always empty. Kotlin also had no partnerships parser and left `extras`/`total` blank.
- Pinned by `CricBuzzFowPartnershipTest`. The Kotlin FOW parser had been dead since the App Router rewrite while its test passed, because the test asserted a hand-written `45-1 (D Warner, 8.2)` blob rather than captured markup.

**A Test side's score is two innings.** "266 & 83/2" is one side's score, and both producers dropped one: the list's `latestInnings` returned `inngs2` if present else `inngs1`, and `match-sync`'s `parseLiveDetail` read `inningsScoreList[0]` and `[1]` — by index, per-team only in limited overs. `teamInningsScore` (`network/TeamInningsScore.kt`) and `teamInningsSides` (`match-sync/src/cricbuzz.js`) aggregate per side joined with `" & "`, dropping the wicket count from a completed innings **in TEST/FC only**; limited-overs output is unchanged. Pinned on both sides by `MultiInningsScoreParityTest`. `parseScore` used to delete `&`, leaving every numeric consumer at zero; it reads the last segment (the innings being batted) and keeps the whole string for display.

**A scraped site's 5xx and a cancelled coroutine are not app errors, and neither is told by its name.** `ScrapeFetcher` throws `ScrapeHttpException(code)`; `isUpstreamOutage` walks the cause chain for a 5xx, and `AppResult.Error.report()` and the ViewModels skip it (ANDROID-54/56) — a 4xx still reports. `SentryOptionsConfig` tests the throwable itself for `CancellationException`: R8 renames library-internal classes, so `type.endsWith("CancellationException")` never matched Compose's in a release build (ANDROID-53, at `PlayerProfileScraper.attemptScrape` catching it as a failed scrape). `ScrollableTabRow`'s default indicator indexes `tabPositions[selectedTabIndex]` unguarded; a row whose tab count changes passes its own (`SearchTabs.kt`, ANDROID-52).
