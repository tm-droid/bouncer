# Match Detail and Commentary UI

## Tabs

**The tab set follows the match, and each fact has one tab** (`MatchTabs.kt`, pinned by `MatchTabsTest`). A fixture opens on Info (Info, Squads, Commentary if any); a match in play on Live (Live, Scorecard, Commentary, Graphs, Squads, Info, Highlights); a finished one on Summary (Summary, Scorecard, Commentary, Graphs, Highlights, Squads, Info). An optional tab appears only with something in it: Graphs only when `hasGraphs` finds a chart with data, Squads once `MatchSquadsSource` answers, Highlights with a clip. The first tab is the default. Overview and AI are gone: Overview had become four tabs in one (state of play, charts, the fall of wickets again, pre-match facts), and AI showed only the win probability Overview already had and the header's run rates.

**The selection is a tab, never an index.** The set changes under the reader: Graphs arrives with the first plotted over, Squads when the page loads, everything when a match starts or ends. The pager is rebuilt with `key(tabs)` at `pageFor(tabs, selected)`, which also sends a reader on Live to Summary when the match ends. Rebuilding (rather than scrolling a live pager) avoids recording the coerced page as a selection when the page count shrinks.

**Where things went.** Live: the batting pair, the current stand (`currentPartnership`: runs and legal balls since the highest-scoring wicket, because the stored wicket numbers are often 0), the last wicket, the bowler, the latest review, the win-probability bar, three lines and "All commentary". Summary: the server's summary and each innings' top two batters and bowlers. Graphs: the probability arc, its key moments and the prediction card, the worm, the manhattan, the phases (which cover the powerplay, so `PowerPlayAnalysisCard` went) and the wagon wheels, newest innings first. The over-by-over comparison card plotted the worm's own series and went. Squads: the team sheet, impact substitutes and Cricinfo's team news. Info: preview, details, toss, officials, forecast, pitch, head to head, ground. Cricbuzz's `matchInfo.state` ("Preview", "Complete") is not shown: it was an "Additional info" row restating the status.

## Detail state

**Every `match-sync` row carries an `updated_at`, and the device reads it.** `getForMatch` and `observeMatch` return `LiveDetailSnapshot`/`ScorecardSnapshot` — payload plus the row's write time — because a row that froze when its match left `live-matches.json` and one written this minute are otherwise identical (the staleness in `eb91dcd`). `updatedAtMs` is null when the column is missing or unparseable, and **null means unknown, never old**: fall back to the prior rule, or one malformed timestamp blanks a live score. `ROW_STALE_MS`/`DETAIL_STALE_MS` are both 3 minutes: an open screen pings presence every 90s, which earns a detail-tier pass every run, so a live row is about a minute old at worst.

**The matches list outranks a row that stopped being written.** `MatchDetailViewModel.onMatchUpdated` is called from composition on every list emission; `listLeadsDetail` (`viewmodels/MatchDetailListSeed.kt`) says yes in exactly three cases: before any payload has arrived, when the list entry has gone terminal, and when the row is older than `DETAIL_STALE_MS`. This is `eb91dcd` the other way: a **live** match `match-sync` is not writing (past `MAX_MATCHES`, or one nobody views) sat on its open-time score while the list advanced, because state is seeded from the list at construction and so is never blank, and `MatchDetailViewV2`'s `ifBlank` fallback could never fire. `seededFrom` touches only fields the list carries: the batting pair, bowler, recent balls and scorecard exist only in the payload, and blanking them would be the same bug again.

**The live payload is oriented to the first-innings side and aligned by team id.** Both score slots and the win probability belong to the side that batted first, while `match.teams` is Cricbuzz's listing order. Do **not** align on names: `inningsScoreList.batTeamName` is a short code ("EZONE" for Central Zone, "RSAA" for South Africa A) that matches nothing under `normalizeTeamName` or `codeMatchesName`, so a name-based swap silently never fires. The payload and `live-winprob` entries carry `team1Id`, `CricketMatch.Team` carries `teamId`, and `viewmodels/MatchLiveDetailAlignment.kt` compares those. `battingTeamIsTeam1` used to compare `current.inningsId` with `isl[0].inningsId`, false for a side batting its *second* innings, so for half of every Test the probability was published against the opposition. It is now `current.batTeamId === isl[0].batTeamId`, the field `firstInningsTeamId` already reads, with the innings-id form only as a fallback for a miniscore with no `batTeamId`.

**A tapped match is an overlay above the NavHost, which stays composed under it.** `BouncerAppContent` used to *swap* `MainAppContainer` for `MatchDetailViewV2`, disposing the back stack, so closing a match opened from a series, search or team landed on Home. The navController is hoisted there, the list poll pauses while the overlay is up (`isCovered`), and the match screen reaches navigation through `LocalOpenSeries`.

**Viewer gate.** `MatchDetailViewModel` pings `bouncer-match-presence` every 90s while a match is open and **not over** — gated on `isMatchOver(match, liveStatus)`, never on `match.isLive`, a frozen list snapshot (same staleness class as `5b86664`). A dead heartbeat means every sync logs "0 with viewers"; it does **not** stop deliveries being stored. `MatchPresenceReporter.ping` leaves a breadcrumb, not an event: every cause is already reported once by `AppwriteClient.executeFunctionDetailed` (uninitialised SDK, guard, FAILED, HTTP status), and the one it skips — the device being offline — was most of what the old capture raised (ANDROID-3M).

## Commentary tab

**The feed is chronological, and chronological is not cricket order.** Rows are ordered by `sort_key` (the Cricbuzz timestamp), so a Test's third-innings over 60 is newer than its second-innings over 80. `CommentaryTabV2` used to regroup with `groupBy { over }.toSortedMap(reverseOrder())`, rendering over 89 directly above over 83. `buildCommentaryBlocks` walks the feed **in order**, opens a block per over, and draws an innings divider where the innings changes: from the `innings` column, or — for older rows — from an over number that *rises* while walking back in time. Never re-sort this feed.

**Never state a figure for a partially-stored over.** `overTotalRuns`/`isMaidenOver` require six legal deliveries present. One stored dot ball rendered as "Over 89 · MAIDEN · 0 runs".

**The `ball` column is the only trustworthy over-and-ball label.** `CommentaryEntry.ball` comes off the row, where `match-sync` writes `ballMetric.label` — `"19.2"`, or The Hundred's `"Ball 72"` (pinned by the smoke probes at `match-sync/src/main.js`). Regexing a leading `40.4` out of the prose does not work: that prefix exists only on AI-rewritten lines, not on raw passthrough rows (`ai_generated = false`), and no over-shaped regex matches The Hundred.

**Dedup must key on the `ball` column, within one ball.** `TimelineEventExtractor.deduplicateByBall` keyed both passes on `ballNumberOf(text)`, so on raw rows every delivery in an over looked like one unnumbered line. Pass 1 collapsed the three separate balls that all read `"Tymal Mills to Matthew Hollard, no run"`; pass 2 compared *across* balls with a prefix floor of `DEDUP_MIN_LENGTH` = 15 characters, the width of `"Tymal Mills to "`, so every short delivery was a "duplicate" of the over's one long line (always the wicket or boundary). Over 18 of ETPL match 169380 rendered two balls of six. Three unit tests asserted that collapse as the contract. `deduplicateByBall` now takes a `ballOf` accessor (`CommentaryParsing` passes the `ball` column), pass 2 compares only within one ball, and `DEDUP_PREFIX_RATIO` is `1.0`, a strict prefix — the real shape of a progressive republish. **Check a dedup change against an over of raw passthrough rows, never distinctly-worded AI prose.**

**A delivery is not one row.** A wide or no-ball carries the label of the legal ball that follows, labels repeat in the next innings, and Cricbuzz republishes corrections under new timestamps. The old dedup keyed on the label alone and kept the *longest* text, so `88.4` wide hid `88.4` FOUR. `deliveryKey` (`CommentaryParsing.kt`) is innings + label, plus the row's `sortKey` for a WIDE/NOBALL, and the **newest** row wins. Pinned by `CommentaryFilterTest`.

**An overturned review is not a wicket.** `TimelineEventExtractor.isWicketLine` reads `outcomeClause` (the field after "<Bowler> to <Batter>,") before any marker in the prose, mirroring `classifyEvent` in `llm.js`; see `match-sync-commentary.md`.

## Cards

**The head-to-head card.** `H2HRepository` lowercased the pair and compared it with keys the trainer writes in original case (none of the 1,732 keys is lowercase), so it never matched; it now indexes case-insensitively on load. The file is the **T20 record only** and used to pool a country's men's and women's sides: a women's pair has its own key (`A|||B|female`) and the card shows on T20 matches only. Every other format reads its own record (right format, right gender) from the match context. Both now sit in one Head to head section on Info, and never together: the context record is shown only when the T20 file did not answer.

**Removed because each was a constant — do not bring back:** the toss card's "venue win %", "H2H toss 3-2" and "Dew factor HIGH"; the prediction card's 85% confidence badge and "Updated: Just now"; the Info tab's weather panel (wind, dew point, visibility hardcoded; temperature and humidity defaulted) with pace/bounce/spin bars scored from keywords in the preview text. The pitch report is shown as written; the forecast and the ground's record come from `mc-{matchId}`.

**Highlights are YouTube embeds, and the embed needs a Referer.** Every row's `embed_url` is `www.youtube.com/embed/{id}` (100 of the newest 100, 2026-10-04). `HighlightPlayerDialog` used to `loadUrl` it directly — a top-level navigation with no Referer, which YouTube answers with "error 153". `youtubeEmbedHtml` (`ui/components/HighlightEmbed.kt`) wraps the player in an iframe loaded with `loadDataWithBaseURL(EMBED_ORIGIN, …)`, the app id as an https origin. There cannot be a native player: YouTube exposes no stream, and downloading or re-hosting breaks its terms, Play policy and the broadcaster's copyright. A clip that still fails reports its code through the IFrame API (150 on the emulator was a video deleted upstream; 9 of those 100 answer 404 on oEmbed) and the dialog offers "Open in YouTube".
