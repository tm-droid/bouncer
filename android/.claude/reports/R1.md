Run 46003010073 (commit 43ae1706, `--cutoffs 2024-03-08,2025-01-27 --latest-season`, label r1). Success; lab.log has 0 "BASELINE MISMATCH" lines.

## Cause
Within one run the crr block (winprob-lab.mjs ~1515-1560) and the e4e8 block (~1566-1612) already shared the baseline object `everything` (fit at ~1490), so they cannot differ inside one process; at e0434dbc both used `everything` (lines 1464/1520/1549 there). The two blocks differed only in the other fits: k48 base `B` was refit (a second `fit` call for the same config) instead of reusing `fits.k48`, and latest-season fits were repeated per block. The E1 (0.37192) vs E4E8 (0.36838) baselines are two different runs, so the gap is cross-run, not a build/fit/score difference between blocks: same row selection (ROW_RATE 0.22, lcg 20261003/771/9091), same trainBinary options (lr 0.02, patience 12 equal build.js:100), same standardiser, temperature on valid, clamp 1e-7, row (not match) weighting in fit, match weighting only in bootstrap. I did not isolate why run 46000590470 gave 0.36838. Run r1 reproduces E1's 0.37192289 exactly, so the lab is deterministic on this corpus and the E4E8 baseline looks like a different corpus/code state at that run (unproven).

## Fix
`fitShared` (memoised by store, groups, class, windows, variant, terms, recal) wraps `fit` (the trainer-faithful path) and every block calls it, so each config is fitted once. `checkBaseline` logs (never throws) when blocks differ by more than 1e-6; results in `report.repro`.
