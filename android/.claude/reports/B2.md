# B2: reduced-overs budget and oversRem notation

## Findings
1. ballNbr is legal balls bowled (disproved suspicion). Fixture `android/app/src/test/resources/cricbuzz_commentary_overball.html`: ODI overs 49.3 with ballNbr 297, overs 50 with ballNbr 300. Fixture `cricbuzz_commentary_hundred.html`: overs 16.4 with ballNbr 100. Pinned by test 1 in `match-sync/test/reduced-overs.test.js`.
2. oversRem notation bug is real in code: `ballsRemainingFor` used `round(oversRemaining*6)`, so 3.4 gave 20 balls, not 22. Limitation: `oversRem` is `$undefined` in every captured fixture (overball, hundred, hundred_innings_end), so the notation is inferred from its sibling `overs`, not verified. B9.md lines 15 and 38 flagged the same.
3. Reduced-overs bug: the payload has no revised-overs field (`revisedTarget:{}` in overball). When `oversRem` is present the budget is right. When it is absent the code fell back to the full format budget (80 balls for a 15-over chase at 20 over).

## Change
- `src/winprob.js`: `ballsRemainingFor` parses oversRemaining with `ballsFromOvers` (cricket notation), falling back to the old rounding only when unparsable. When oversRemaining is absent, derives balls as `round(runsNeeded / requiredRunRate * 6)` if that is positive and below the format budget.
- `src/main.js`: `liveSituationArgs` passes `runsNeeded` and `requiredRunRate`. `chaseStart` treats `oversRemaining === 0` with `ballsBowled` below the allotment as a finished reduced innings and uses `ballsBowled` as the allotment.
- `test/reduced-overs.test.js`: 4 tests.
